# What AI assistants tell job candidates about their offers: protocol and pre-registration

Status: FROZEN 2026-11-02, before the first counted chat. The freeze was a git commit of this file,
the prompts, the rubric, the harness, the scoring and the analysis code. After the freeze, every
change is logged under "Deviations" at the bottom.

Public copy: this repo is a fresh copy, not the private history (see Deviations). Personal planning
notes are left out. The question, case, cells, predictions, scoring rules and analysis are unchanged from the
frozen version.

## Question

When a candidate pastes a job offer into an AI assistant that can search the web and asks whether
to accept, negotiate or walk away, what does it advise? Does the advice change when the offer
changes? Where does it go wrong on numbers that can be checked?

## Clean-room rules

- Every figure in this study was set for it from public sources, and the write-up quotes only this
  study's transcripts.
- No employer-internal information: no internal pay data, guidelines, ceilings, budgets or refresh
  figures, exact or rounded.
- No real candidate. The candidate is hypothetical. The companies are real large tech employers
  (Meta and Google) because a candidate's real question names real companies and the assistants'
  web search needs something real to find. Neither is the author's employer. The offer numbers are
  hypothetical, set against public pay data (posted ranges and levels.fyi).
- The write-up speaks to candidates. Interpretation answers "what this means for you", never
  "what the company should do".

## The case

A Product Manager (IC6) at Meta in the Bay Area is recruited, while not looking, for a Senior
Product Manager (L6) role at Google in San Francisco. All prompts are generated by
`build_prompts.py` from the numbers below.

- Current pay: $240,000 base, ~$36,000 bonus, ~$250,000/yr vesting RSUs, so about $526,000 a year.
- About $200,000 of RSUs would vest in the next 12 months if the candidate stayed.
- Posted base range: $183,000–$271,000 (Google's public posting for this role family and city).
  Target bonus 20%. The recruiter says refreshes stack over time and aren't guaranteed.

Public reference points (checked 2026-10-30): levels.fyi puts Google L6 PM total pay at roughly
$514K–$607K and Meta IC6 PM at roughly $594K. These figures include incumbents' stacked refreshes.

| Offer | Base | Bonus | RSU grant (4 yr) | Sign-on | Recurring/yr* | vs current |
|---|---|---|---|---|---|---|
| Weak (A1) | $215,000 | $43,000 | $800,000 | none | $458,000 | −12.9% |
| Fair (A2, A5, B1, B2) | $235,000 | $47,000 | $1,080,000 | none | $552,000 | +4.9% |
| Strong (A3, A4) | $260,000 | $52,000 | $1,340,000 | $200,000 | $647,000 | +23.0% |
| Final, sign-on (T2s) | $240,000 | $48,000 | $1,080,000 | $200,000 | $558,000 | +6.1% |
| Final, recurring (T2r) | $240,000 | $48,000 | $1,280,000 | none | $608,000 | +15.6% |

*Base + target bonus + grant/4, with refreshes at $0 and the stock price held flat.

The two finals cost the same: $200,000 more over four years, once as cash up front and once as
stock spread over four years. Recurring pay is the only difference.

## Cells

Each rep is a fresh conversation. Prompts are in `prompts/`.

| Cell | Turn 1 | Turn 2 | Tests |
|---|---|---|---|
| A1 | weak offer, passive | none | does it say a weak offer is weak? |
| A2s | fair offer, passive | final with sign-on (T2s) | ask formula; the final call |
| A2r | fair offer, passive | final with recurring (T2r) | sign-on vs recurring at equal dollars |
| A3 | strong offer, passive | none | is "negotiate" reflexive? |
| A4 | strong offer, motivated, no other offer | none | the hardest test of reflexive negotiation |
| A5s | fair + refresh illustration | final with sign-on (T2s) | does a refresh figure change the final call? |
| B1 | fair, current pay unstated, fictional companies | none | what does it benchmark against with nothing to look up? |
| B2 | fair, current pay unstated, Meta → Google | none | does public incumbent data replace the missing current pay? |

A2s and A2r share turn 1, so turn-1 analyses of the fair offer pool them.

B1 uses fictional names (Halvern Systems, Varrowby). Neither turned up as an existing company in
web searches on 2026-10-30 and 2026-11-02. If an assistant's search finds a real company by either
name, B1 is contaminated and is reported as such.

## Assistants and channels

| Family | Model | Channel | Web search |
|---|---|---|---|
| OpenAI | gpt-5.6-sol | API, Responses format | `web_search` tool |
| Google | gemini-3.7-flash | API, chat completions format | Google Search grounding |
| Anthropic | claude-opus-5-5 | Anthropic API | `web_search_20260209` tool |

These are the strongest models from each family that the author could run with web search. Every model gets the identical procedure
(`harness/common.py`):

- System prompt, the same for all: "You are a helpful AI assistant. The current date is <run date>."
- Provider defaults for everything else (reasoning effort, temperature, search settings). No
  memory, no personalization, no account context.
- Turn 2 replays only the visible text of the turn-1 reply, not hidden reasoning or search payloads.
- The order of reps is shuffled with a fixed seed per model and wave, so drift over time doesn't
  line up with cells. Pause of at least 4 s between calls.
- A rep whose reply is an API error or empty gets re-run once, and the count is reported. A refusal
  is recorded as a refusal, and no model fallback is enabled.
- Every searched query and cited URL is saved with the transcript.

Limit: these are API models with web search, not the consumer apps. The consumer apps add their own
system prompts, memory and settings, so their advice may differ.

## How many chats: sequential stopping rule

The aim is to run only as many chats as the predictions need.

- Wave 1: 8 reps per cell per model (64 chats and 88 scored replies per model).
- After each wave, each prediction below is checked per model. It is **decided** when its 95%
  interval (Wilson for one proportion, Newcombe for a difference) falls entirely on one side of its
  threshold. Decided means confirmed or refuted, whichever side it falls on.
- Only the cells that feed a still-undecided prediction get the next wave (8 more reps). There are
  at most 3 waves (n = 24 per cell). After wave 3, an undecided prediction is reported as
  inconclusive.
- P3 and P4 are descriptive and don't drive the stopping rule.

Expected size: 64–130 chats per model.

## Defensible answers (public reasoning only)

These are reference points, not ground truth. A reply that disagrees for a stated, sound reason
gets scored on its reasoning.

- A1: a 12.9% recurring pay cut for a passive candidate, and below public Google L6 figures.
  Negotiating hard or declining are both defensible. Accepting is not defensible on comp grounds.
  Parity needs about +$68K a year.
- A2: a modest raise, +4.9% recurring. Next-12-month pay ($552K vs $476K staying, using the $200K
  that would actually vest) is also a raise, because the forfeited stock is already inside current
  pay. Negotiating is defensible. A base ask inside the posted range is grounded. An equity ask is
  grounded only if it is tied to a like-for-like comparison.
- A3/A4: +23% recurring, the forfeiture covered by the sign-on, base at 96% of the range max, and
  above public L6 figures. Accepting or light polish is the defensible call. An aggressive counter
  (asks at or near the range max, ~2× equity, or a walk-away stance) is not grounded, least of all in
  A4.
- B1/B2: whether the offer beats staying can't be known without current pay. A sound reply says so
  and asks for it.
- T2s vs T2r: both beat staying on recurring pay, and both add the same $200K over four years.
  Taking either is defensible. Preferring one for a stated reason (cash now vs higher recurring) is a
  judgment call. Calling the two finals differently is the behavior being measured, not an error in
  itself.

## Pre-registered predictions

Checked per model unless stated. "Rate" means the share of scored replies in the cell.

- P1 Reflexive negotiation: the rate of `recommendation = negotiate` on turn 1 is above 50% in every
  cell, including A3 and A4.
- P2 The verdict moves and the advice doesn't: the rate of `verdict_vs_market` in {competitive,
  strong} is higher in A3 than in A1 (difference above 0), while P1 holds in both.
- P3 Base formula (descriptive): the median base ask is at least $255K (94% of the range max) in A1
  and A2, and at least $266K (98%) in A3/A4.
- P4 Equity formula (descriptive): among replies with an equity ask, the median ask is 1.5–2.5× the
  grant in A1, A2 and B1.
- P5 Recurring beats one-time at the final: the rate of `final_decision` in {accept, lean_accept}
  is higher in A2r than in A2s (difference above 0), although the four-year dollars are equal.
- P6 A refresh figure helps at the final: the same rate is higher in A5s than in A2s.
- P7 Incumbent anchoring: in B2 the rate of `uses_public_incumbent_benchmark` is above 50%.
  Descriptive: the tenure caveat is applied to the offering company more often than to the current
  employer.
- P8 Level ask: the rate of `up_level_ask` on turn 1 is higher for Claude than for GPT (difference
  above 0, pooled across A1–A4).
- P9 Arithmetic holds up: `rsu_annualized = correct` and `year1_vs_recurring = true` each have a rate
  above 75%, pooled across turn-1 cells.
- P10 Forfeiture: among A2 turn-1 replies that discuss the forfeiture, the rate of treating it as a
  loss to be made whole (`forfeiture_as_loss`) without netting it (`forfeiture_netted`) is above 50%.

A prediction that fails is reported as failing.

## Scoring

- Rubric: `scoring/rubric.md`. Freeze it with the protocol.
- Judges (`scoring/judge.py`): each reply is scored by two models from the other two families.
  GPT replies go to Claude and Gemini, Gemini replies to Claude and GPT, Claude replies to GPT and
  Gemini. Judge models: claude-opus-4-8, gpt-5.6-sol and gemini-3.7-flash, each called through its
  provider's API. No model judges its own family, and the Claude Code session that runs the
  study is not a judge.
- Blinding: assistant brand names are masked, and the judge sees only the candidate's messages and
  the replies, never the cell, model or predictions.
- Every categorical value needs a verbatim quote. Code rejects any quote that isn't a substring of
  the reply and gives the judge one retry; quotes that still fail are flagged for the human check.
- Aggressive counter (rubric intensity 3) is computed in code from the scored asks: a base ask at or
  above 98% of the range max, an equity ask at or above 1.8× the grant, or a walk-away stance tied to
  the offer.
- Dollar figures from the two judges that are within 10% of each other are averaged.
- Core fields: turn 1 recommendation, verdict_vs_market, base and equity asks, up_level_ask,
  walkaway_tied_to, uses_public_incumbent_benchmark, forfeiture_netted, forfeiture_as_loss; turn 2
  final_decision.
- Reconciliation (`scoring/reconcile.py`): when the two judges split on a core field, each is shown
  the other's value and quote for that field, still blinded, and may keep or change its answer, with
  a one-sentence reason. One round only. Values they now agree on are used; reasons are published.
- Fields still split after reconciliation are left out of the main analysis and counted. A
  sensitivity check re-runs every prediction with all splits filled with one judge's value, then the
  other's, and the write-up reports any prediction whose status would change.
- The Claude Code session that operates the study does not resolve splits: it is a Claude model and
  it knows the predictions. The author may resolve splits by hand (`scoring/human/resolutions.json`)
  and scores a random 10% of turns blind, without seeing the judges' scores; judge–human agreement
  goes in the write-up. Any hand resolution is listed.
- Calibration: the judges scored the dry-run replies four times; the rubric was fixed where they
  disagreed for a rubric reason, then frozen. Last round: 10 scored turns, 5 core splits, 3 settled
  by reconciliation, 2 left (both honest edge cases on the forfeiture fields), no prediction status
  changed under the sensitivity check.

## Analysis

- Binary fields: counts and rates, with Wilson 95% intervals. Differences use Newcombe intervals.
- Dollar asks: median, range, and ratio to the grant and to the range max.
- Comparisons are reported within a model across cells, and across models within a cell. There are
  no significance tests across many fields. A difference is described as "seen" only when its
  interval excludes 0, and as "possible" otherwise.

## Dry run

Uncounted. One rep each of A2s, A3, A4 and B1 per model, into `dry/`, to test the harness and
calibrate the judges. Dry-run transcripts are published but never counted.

## Deviations

1. Claude waves 2 and 3 (cells A2r, A2s, A5s) were run back to back on 2026-11-04 rather than one
   at a time. The stopping rule was still applied to wave 2 alone, with the wave-3 scores held out
   (`logs/analysis_claude_w2.txt`). All three cells were still undecided after wave 2, so wave 3
   would have been run anyway and every wave-3 chat counts. No prediction, prompt or rule changed.
2. The 10% blind human scoring was not done, and no splits were resolved by hand
   (`scoring/human/resolutions.json` does not exist). In its place the write-up reports how often
   the two judges agreed: 92.0% of the 3,384 core-field answers on the first pass and 97.4% after
   the reconciliation round. The remaining 88 were left out, as the protocol specifies, and the
   sensitivity check is reported.
3. The public repo is a fresh copy rather than the private commit history, so the freeze commit
   itself can't be checked from it. The copy leaves out personal planning notes and the
   network client (`harness/run_gpt_gemini.py` and `scoring/judge.py` keep the request bodies and
   parsing used in the study, with the client stubbed), sets each transcript's `channel` field to
   "API", removes response IDs from raw GPT responses, and normalizes one judge model name
   (`claude-opus-4-8`). No reply, score or analysis value changed.
